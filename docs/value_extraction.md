# Value extraction ladder

How a forecast VALUE gets out of a model's rationale: the four-rung ladder in
`metaculus_bot/value_extraction.py`, the fidelity checks each rung has to pass, and
the two per-forecast log markers (`EXTRACTION_RUNG` and `MEMBER_FORECAST`) that make
extraction behaviour auditable after the fact. The fenced ```json STRUCTURED FORECAST
block is the authoritative source and the parser LLM is salvage only. Read this
before touching a rung, a validator, or either marker's format string: the markers
are archive keys as well as log lines, so their spelling is a data contract.

Last verified against the code on 2026-09-03.

## The ladder

Since 2026-07-10, forecast values (binary probability, MC option probabilities, numeric percentiles) come out of the fenced ```json STRUCTURED FORECAST block via a deterministic four-rung ladder — the block is the authoritative source, and the parser LLM survives only as a salvage rung. `extract_binary`, `extract_mc`, and `extract_numeric` share the same driver and are called by both `forecaster_runners.py` (per-model forecasts) and `stacking.py` (stacker output), so both flows share one extraction path:

1. **block** — deterministic parse of the fenced ```json block (`parse_structured_block`: `json.loads` + Pydantic validation against `BinaryStructured` / `MultipleChoiceStructured` / `NumericStructured`). This absorbs the old numeric_format_router F5 block-lift: when the schema-valid numeric block carries a `declared_percentiles` dict, it is lifted directly into `Percentile(percentile=..., value=...)` objects.
2. **repair** — deterministic JSON repair (`json_repair`) of a malformed fenced block, or a balanced-braces scan of the rationale's trailing `_TAIL_SCAN_CHARS` when no fence survived. The repair must be a REPAIRER, not an author: `_repair_infidelity_reason` refuses any candidate carrying a truncated numeric literal (a rationale cut mid-decimal leaves `"posterior_prob":0.`, which `json_repair` completes to `0.0` — a value that passes bounds validation and would publish as the binary clamp floor), and refuses any repair whose numeric-token stream INTRODUCES a number the raw candidate didn't have.
3. **llm** — the existing LLM parser (`parse_structured`) run over the full rationale as a last-resort salvage. **Post-rung validation is a FIDELITY check, not just a shape check.** The LLM rung decodes under a schema, so handed a rationale with no forecast in it it *must* emit numbers — "absent" is not expressible — which is why shape alone was never enough: presence, bounds, set-membership and sum-to-1 do not establish that a salvage matches the rationale. Numeric values must also be finite and ordered by their percentile labels; ties are allowed, while a decrease fails the rung before `sort_by_percentile_level` and downstream sanitisation. MC must be non-empty and match the question's option set. The ladder raises when these fidelity checks fail, so the forecaster drops rather than publishing a manufactured value.
4. Raise `ValueExtractionError` — the numeric forecaster (or the stacker) has no usable value source; the caller drops or soft-fails the forecaster exactly as parser failures propagated before the ladder.

## The two per-forecast markers

Every successful extraction emits one `EXTRACTION_RUNG: question=... model=... qtype=... rung=... block_present=...` INFO log line — this is the drift-signal telemetry that superseded the deleted shadow-divergence comparison. Watch `rung=llm` salvages and `block_present=false` in prod logs; those are the two symptoms that indicate a forecaster stopped emitting a well-formed block. Beside it, since 2026-09-02, one `MEMBER_FORECAST: question=... model=... role=member|stacker qtype=binary|multiple_choice|numeric raw=... published=...` INFO line per forecast VALUE (`metaculus_bot/member_forecast.py` `format_member_forecast_marker`; emitted by the three runners in `forecaster_runners.py` for every member, by `stacking.py` for the stacker's binary and MC output, and by `aggregation_pipeline._run_stacking_numeric` for the stacker's numeric output, since that is where its percentiles are sanitised). `raw` is the value the extraction ladder read off the rationale before any clamp, renormalise or sanitise; `published` is what the runner hands onward. Binary carries a probability each (`raw=0.005 published=0.02`); MC the option-probability vector in `question.options` order (`raw=[0.9,0.005,0.095]`), which the ladder hands back as `ExtractionOutcome[McForecast].value.declared_probs` beside the constructible list (`McForecast.option_list`; the pairing is the MC outcome's TYPE, so no consumer checks for it), because a `PredictedOptionList` is clamped on construction and the runner never holds the raw vector on the list itself (on the LLM rung's strict sub-path it is the parser's output after ft's construction clamp); numeric the declared `[percentile, value]` pairs with the percentile as the block's decimal (`raw=[[0.025,9.2],...]`, never the percent label, whose float multiply leaves `10.000000000000002` on the 0.1 anchor) and `published` the post-`sanitize_percentiles` list. Both values are whitespace-free compact JSON literals kept VERBATIM in the archive through the spec's per-spec `raw_fields` (the global `_RAW_FIELDS` is keyed by name and `THIN_PUBLISH_FLOOR` spells a float field `raw` too), so a consumer always `json.loads` them; harvested as `member_forecast`. The numeric line precedes the unit-mismatch guard on purpose: a member that guard withholds still leaves its raw declaration, which is exactly what an audit of the guard needs, and the drop is in `FORECASTER_DROPS` (restrict to members that reached the aggregate via `FORECASTERS_SURVIVED`'s `models`). The reason is the 2026-09-02 clip-threshold re-read (what a looser `BINARY_PROB_MIN` would have done): no marker carried a member's value on every question (`EXTREME_CALL` only past the band, `THIN_PUBLISH_FLOOR` only the lone-survivor case, the runner's own `Forecasted URL` line the CLAMPED value with no model name), so a raw binary probability was recoverable only from the published comment's per-rationale fenced block, which is middle-trimmed at `COMMENT_CHAR_LIMIT`, publishes a stacked question's members as sub-blocks, and carries the block only since 2026-05-19. That left 74 of 451 resolved binaries with any raw value and the 377 older ones with none anywhere; on the 179 block-era records the block-aware trim did preserve every bulleted member's block on binary, MC and discrete questions, while 9 of 50 numeric comments had lost members to the retired tier-2 block schema (`mixture_components` / `tails` blocks with no `declared_percentiles`, or blocks with trailing content that fail `json.loads`). Receipts: `scratch/residual_2026-09-01/clip_threshold/member_value_gap.py`.
## What the ladder does NOT decide

Discrete-integer snapping is decided separately by the C3 block-read in `forecaster_runners.run_numeric_forecast` — it reads `NumericStructured.outcome_type` directly before falling back to a parser LLM call for `OutcomeTypeResult`, and the ladder does not touch that path.
