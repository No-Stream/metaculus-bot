# Value extraction ladder

How a forecast VALUE gets out of a model's rationale: the four-rung ladder in
`metaculus_bot/value_extraction.py`, the fidelity checks each rung has to pass, and
the two per-forecast log markers (`EXTRACTION_RUNG` and `MEMBER_FORECAST`) that make
extraction behaviour auditable after the fact. The fenced ```json STRUCTURED FORECAST
block is the authoritative source and the parser LLM is salvage only. Read this
before touching a rung, a validator, or either marker's format string: the markers
are archive keys as well as log lines, so their spelling is a data contract.

Last verified against the code on 2026-09-03.

## The ladder

Since 2026-07-10, forecast values (binary probability, MC option probabilities, numeric percentiles) come out of the fenced ```json STRUCTURED FORECAST block via a deterministic four-rung ladder — the block is the authoritative source, and the parser LLM survives only as a salvage rung. `extract_binary`, `extract_mc`, and `extract_numeric` share the same driver and are called by both `forecaster_runners.py` (per-model forecasts) and `stacking.py` (stacker output), so both flows share one extraction path:

1. **block** — deterministic parse of the fenced ```json block (`parse_structured_block`: `json.loads` + Pydantic validation against `BinaryStructured` / `MultipleChoiceStructured` / `NumericStructured`). This absorbs the old numeric_format_router F5 block-lift: when the schema-valid numeric block carries a `declared_percentiles` dict, it is lifted directly into `Percentile(percentile=..., value=...)` objects.
2. **repair** — deterministic JSON repair (`json_repair`) of a malformed fenced block, or a balanced-braces scan of the rationale's trailing `_TAIL_SCAN_CHARS` when no fence survived. The repair must be a REPAIRER, not an author: `_repair_infidelity_reason` refuses any candidate carrying a truncated numeric literal (a rationale cut mid-decimal leaves `"posterior_prob":0.`, which `json_repair` completes to `0.0` — a value that passes bounds validation and would publish as the binary clamp floor), and refuses any repair whose numeric-token stream INTRODUCES a number the raw candidate didn't have.
3. **llm** — the existing LLM parser (`parse_structured`) run over the full rationale as a last-resort salvage. **Post-rung validation is a FIDELITY check, not just a shape check.** The LLM rung decodes under a schema, so handed a rationale with no forecast in it it *must* emit numbers — "absent" is not expressible — which is why shape alone was never enough: the earlier claim that "the parser can never smuggle in a fabricated value" was false as written, because presence/bounds/set-membership/sum-to-1 say nothing about faithfulness to the rationale. Numeric values must now additionally be FINITE and ordered the way their labels claim (ties allowed — a repeated value is a legitimate concentrated declaration; a strict DECREASE with rising percentile is incoherent and fails the rung, because `sort_percentiles_by_value` sorts by LABEL and so never reorders a value-disordered set — it force-monotonizes it, which on one out-of-place value pinned 10 of 13 percentiles at a bound and published). MC must be non-empty and match the question's option set: a rung-3 parse validating an EMPTY option list used to reach `build_mc_prediction`, which imputed exact 1/n on every option — a uniform forecast nobody made, which then passed every downstream check. That fallback now RAISES and the forecaster drops.
4. Raise `ValueExtractionError` — the numeric forecaster (or the stacker) has no usable value source; the caller drops or soft-fails the forecaster exactly as parser failures propagated before the ladder.

## The two per-forecast markers

Every successful extraction emits one `EXTRACTION_RUNG: question=... model=... qtype=... rung=... block_present=...` INFO log line — this is the drift-signal telemetry that superseded the deleted shadow-divergence comparison. Watch `rung=llm` salvages and `block_present=false` in prod logs; those are the two symptoms that indicate a forecaster stopped emitting a well-formed block. Beside it, since 2026-09-02, one `MEMBER_FORECAST: question=... model=... role=member|stacker qtype=binary|multiple_choice|numeric raw=... published=...` INFO line per forecast VALUE (`metaculus_bot/member_forecast.py` `format_member_forecast_marker`; emitted by the three runners in `forecaster_runners.py` for every member, by `stacking.py` for the stacker's binary and MC output, and by `aggregation_pipeline._run_stacking_numeric` for the stacker's numeric output, since that is where its percentiles are sanitised). `raw` is the value the extraction ladder read off the rationale before any clamp, renormalise or sanitise; `published` is what the runner hands onward. Binary carries a probability each (`raw=0.005 published=0.02`); MC the option-probability vector in `question.options` order (`raw=[0.9,0.005,0.095]`), which the ladder hands back as `ExtractionOutcome[McForecast].value.declared_probs` beside the constructible list (`McForecast.option_list`; the pairing is the MC outcome's TYPE, so no consumer checks for it), because a `PredictedOptionList` is clamped on construction and the runner never holds the raw vector on the list itself (on the LLM rung's strict sub-path it is the parser's output after ft's construction clamp); numeric the declared `[percentile, value]` pairs with the percentile as the block's decimal (`raw=[[0.025,9.2],...]`, never the percent label, whose float multiply leaves `10.000000000000002` on the 0.1 anchor) and `published` the post-`sanitize_percentiles` list. Both values are whitespace-free compact JSON literals kept VERBATIM in the archive through the spec's per-spec `raw_fields` (the global `_RAW_FIELDS` is keyed by name and `THIN_PUBLISH_FLOOR` spells a float field `raw` too), so a consumer always `json.loads` them; harvested as `member_forecast`. The numeric line precedes the unit-mismatch guard on purpose: a member that guard withholds still leaves its raw declaration, which is exactly what an audit of the guard needs, and the drop is in `FORECASTER_DROPS` (restrict to members that reached the aggregate via `FORECASTERS_SURVIVED`'s `models`). The reason is the 2026-09-02 clip-threshold re-read (what a looser `BINARY_PROB_MIN` would have done): no marker carried a member's value on every question (`EXTREME_CALL` only past the band, `THIN_PUBLISH_FLOOR` only the lone-survivor case, the runner's own `Forecasted URL` line the CLAMPED value with no model name), so a raw binary probability was recoverable only from the published comment's per-rationale fenced block, which is middle-trimmed at `COMMENT_CHAR_LIMIT`, publishes a stacked question's members as sub-blocks, and carries the block only since 2026-05-19. That left 74 of 451 resolved binaries with any raw value and the 377 older ones with none anywhere; on the 179 block-era records the block-aware trim did preserve every bulleted member's block on binary, MC and discrete questions, while 9 of 50 numeric comments had lost members to the retired tier-2 block schema (`mixture_components` / `tails` blocks with no `declared_percentiles`, or blocks with trailing content that fail `json.loads`). Receipts: `scratch/residual_2026-09-01/clip_threshold/member_value_gap.py`. A sibling WARN, `OPEN_BOUND_PILING: question=... model=... bound=... bin_mass=... declared_edge=... bound_value=...` (`numeric/diagnostics.py`, threshold `OPEN_BOUND_PILING_THRESHOLD` in `numeric/config.py`), fires when a model piles at least that fraction of mass on the terminal displayed bin of an *open*-bound numeric question without declaring any percentile beyond the edge — the "crammed the open ceiling" failure mode fixed 2026-07-12 by rendering nominal/displayed bounds in the numeric prompts (`nominal_bounds` in `numeric/utils.py`). It takes the pre-resample model-declared percentiles explicitly (the discrete resample overwrites `prediction.declared_percentiles` with a grid pinned to the raw bounds, which would defeat the above-edge exemption). Since 2026-07-12 every bot-run workflow tees stdout+stderr to a `run_logs/` artifact, so this telemetry is durably grep-able after the fact; as of 2026-08-03 that artifact is named `research-<run_id>` in all of them (the two test workflows used `logs-<run_id>` before that, and `RUN_LOG_ARTIFACT_PREFIXES` still harvests those). Runs also emit OpenRouter credit telemetry (`metaculus_bot/credit_telemetry.py`, wired in `cli.py`): `CREDIT_BALANCE: key=... phase=start|end remaining=... usage=...` per key, `CREDIT_SPEND: key=... run_delta_usd=... remaining=...` at end of run, and a `CREDIT_FLOOR_BREACH` WARN when the donated key drops below `OPENROUTER_CREDIT_FLOOR_USD` (constants.py) — a breach lets the run complete/publish normally, then exits non-zero as a refill reminder ONLY when credit alerting is active (see below). Beside `CREDIT_SPEND`, one `CREDIT_ROLE_SPEND: role=... key=... usd=... calls=... costed_calls=... byok_usd=...` line per (role, key) says WHERE the run's OpenRouter dollars went (since the 2026-09 bundle): every LLM built through `build_llm_with_openrouter_fallback(..., role=...)` (and the raw-acompletion gap-fill v2 driver) stamps a litellm `metadata=` tag, and a litellm success callback (`RoleSpendTracker`) reads OpenRouter's own per-call `usage.cost` + `cost_details.upstream_inference_cost` off the response — the provider's accounting, not litellm's price table. `usd=n/a` means the calls carried no cost data (never a fabricated zero); `role=untagged` means a builder call site forgot its `role=`. Gemini grounded search, v2's `read_document`, AskNews and Exa are not OpenRouter and are not in this ledger. litellm enqueues success callbacks onto a logging worker bound to the running event loop, which `asyncio.run` tears down on return, so `cli.py` wraps each forecast in `_forecast_with_callback_drain` (bounded by `LITELLM_CALLBACK_DRAIN_TIMEOUT_S`) and takes a coroutine FACTORY so the coroutine is created inside the loop; without the drain the last calls' rows are lost. Harvested as `credit_role_spend`; `scripts/reconcile_credit_spend.py --roles` tabulates it against settled per-run spend.

## What the ladder does NOT decide

Discrete-integer snapping is decided separately by the C3 block-read in `forecaster_runners.run_numeric_forecast` — it reads `NumericStructured.outcome_type` directly before falling back to a parser LLM call for `OutcomeTypeResult`, and the ladder does not touch that path.
