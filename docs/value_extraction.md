# Value extraction ladder

How a forecast VALUE gets out of a model's rationale: the four-rung ladder in
`metaculus_bot/value_extraction.py`, the fidelity checks each rung has to pass, and
the two per-forecast log markers (`EXTRACTION_RUNG` and `MEMBER_FORECAST`) that make
extraction behaviour auditable after the fact. The fenced ```json STRUCTURED FORECAST
block is the authoritative source and the parser LLM is salvage only. Read this
before touching a rung, a validator, or either marker's format string: the markers
are archive keys as well as log lines, so their spelling is a data contract.

Last verified against the code on 2026-09-09.

## The ladder

Since 2026-07-10, forecast values (binary probability, MC option probabilities, numeric percentiles) come out of the fenced ```json STRUCTURED FORECAST block via a deterministic four-rung ladder — the block is the authoritative source, and the parser LLM survives only as a salvage rung. `extract_binary`, `extract_mc`, `extract_numeric`, since 2026-09-08 `extract_date`, and since 2026-09-09 `extract_pmf` (the per-bin ladder, next section) share the same driver and are called by both `forecaster_runners.py` (per-model forecasts) and `stacking.py` (stacker output), so both flows share one extraction path. `extract_date` mirrors `extract_numeric` and returns epoch-second percentiles (the question's `numeric.date_axis` view), so nothing downstream of the ladder ever sees a date.

The `question_type` a block may declare is `structured_output_schema.BlockType`: every `question_types.QuestionType` token plus `pmf`. `pmf` is a BLOCK type, not a question type, because a per-bin block is how a coarse-grid numeric or date question is elicited, not a kind of question; `QuestionType` itself is unchanged and keeps typing the question everywhere else (`MEMBER_FORECAST`'s `qtype`, `question_type_of`, the gap-fill ghost types, the tool runner). `tests/test_structured_output_schema.py::TestQuestionTypeVocabulary` pins that the model map's keys are exactly the question types plus `pmf`, that the three parsers are annotated with `BlockType`, and that no restated copy of the vocabulary exists.

1. **block** — deterministic parse of the fenced ```json block (`parse_structured_block`: `json.loads` + Pydantic validation against `BinaryStructured` / `MultipleChoiceStructured` / `NumericStructured` / `DateStructured` / `PmfStructured`). This absorbs the old numeric_format_router F5 block-lift: when the schema-valid numeric block carries a `declared_percentiles` dict, it is lifted directly into `Percentile(percentile=..., value=...)` objects. `DateStructured`'s values are ISO strings parsed through `numeric.date_axis.parse_forecast_date` and nothing else (UTC always, never host-local; a date-only value means noon UTC of that day, so its mass lands inside that day's right-closed bin). That parse is also the truncation guard for dates: the repair rung's numeric-literal check below is vacuous on strings, so a rationale cut mid-date fails the ISO parse instead of completing to a wrong day. Three decode-time refusals (since 2026-09-09) keep an ambiguous block off this rung: an object that repeats a key fails the decode (`json.loads` is last-write-wins by default, so `{"0": 0.9, "0": 0.4, "1": 0.6}` would otherwise read as a valid vector nobody declared), an explicit `"question_type": null` is a mismatch like any other wrong literal (only an ABSENT key is the caller's to fill in), and the value-bearing probability fields (`posterior_prob`, `option_probs`, `bin_probs`) refuse a JSON boolean, which pydantic's lax float would otherwise read as 1.0 / 0.0. Detail under "Block schemas: design notes".
2. **repair** — deterministic JSON repair (`json_repair`) of a malformed fenced block, or a balanced-braces scan of the rationale's trailing `_TAIL_SCAN_CHARS` when no fence survived. The repair must be a REPAIRER, not an author: `_repair_infidelity_reason` refuses any candidate carrying a truncated numeric literal (a rationale cut mid-decimal leaves `"posterior_prob":0.`, which `json_repair` completes to `0.0` — a value that passes bounds validation and would publish as the binary clamp floor), and refuses any repair whose numeric-token stream differs from the raw candidate's as a multiset, in EITHER direction. An introduced number is an invented value. A dropped number is how a repeated key surfaces: `json_repair` re-serialises through a Python dict, so it collapses `{"0": 0.9, "0": 0.4}` to `{"0": 0.4}` with `0.9` gone from the stream, and since the strict rung has already refused the repeated key, a one-directional check would have published the collapsed block as `rung=repair` (the codex Wave C bug hunt found this on the pmf block; `tests/test_value_extraction.py::TestSalvageFidelity` and `tests/test_pmf_extraction.py` pin both the well-formed and the trailing-comma shape). The check was one-directional until 2026-09-09 on the reasoning that the schema catches a missing field, which is false for the dict-valued probability fields, where a dropped entry is just a smaller dict. The known cost of symmetry: a block carrying a numeric literal inside a JSON comment (`// was 0.4`) now goes to the paid LLM rung instead of repairing, because the lexer cannot tell a comment from value position; no such block has been observed, and a wrong published value outweighs a parser call. `_COMPLETE_NUMBER_RE` is what "complete" means in that check: a full JSON number, optionally with a leading-dot fraction such as `.5`, since a leading-dot fraction is the one shape `json_repair` completes without changing the value. The truncated forms `0.`, `.`, `1e` and `1e-` are rejected deliberately, because those are exactly the shapes it completes by inventing the missing digits.
3. **llm** — the existing LLM parser (`parse_structured`) run over the full rationale as a last-resort salvage; on a date question the salvage schema is `IsoDatePercentile` (`structured_parse.py`), forecasting-tools' `DatePercentile` with its value parsed through the same `parse_forecast_date`, so the LLM rung carries the block rung's UTC and noon semantics. **Post-rung validation is a FIDELITY check, not just a shape check.** The LLM rung decodes under a schema, so handed a rationale with no forecast in it it *must* emit numbers — "absent" is not expressible — which is why shape alone was never enough: presence, bounds, set-membership and sum-to-1 do not establish that a salvage matches the rationale. Numeric values must also be finite and ordered by their percentile labels; ties are allowed, while a decrease fails the rung before `sort_by_percentile_level` and downstream sanitisation. MC must be non-empty and match the question's option set. The ladder raises when these fidelity checks fail, so the forecaster drops rather than publishing a manufactured value.
4. Raise `ValueExtractionError` — the numeric forecaster (or the stacker) has no usable value source; the caller drops or soft-fails the forecaster exactly as parser failures propagated before the ladder.

## The per-bin ladder (`pmf`)

On an enumerable Mantic grid (`numeric.config.elicit_per_bin`: an outcome-space grid of `PMF_ELICITATION_MAX_BINS` bins or fewer on a platform in `PMF_ELICITATION_PLATFORMS`) a forecaster is asked for one probability per bin instead of thirteen percentiles, and the block reads `{"question_type": "pmf", "bin_probs": {<label>: <prob>, ...}}`. The keys are the labels of `numeric.pmf_grid.PmfGrid.keys`: one per bin in grid order, with `below_range` first when the lower bound is open and `above_range` last when the upper bound is open (the reserved keys are `PMF_BELOW_RANGE_KEY` / `PMF_ABOVE_RANGE_KEY` in `constants.py`). `PmfStructured` checks only that the object is a probability vector (non-empty, string keys, every value a number in [0, 1], never a JSON boolean, sum within `pmf_prob_sum_tolerance(key_count)` of 1.0, no other top-level key), through the same `_validate_probability_dict` the multiple-choice ballot uses; matching the keys onto the grid is the ladder's job. The sum tolerance scales with the key count: the larger of the multiple-choice ballot's 0.02 and 0.005 per key (`_PMF_PROB_SUM_TOLERANCE_PER_KEY`), because a forecaster who rounds every probability to two decimals drifts by up to 0.005 a key and a block may carry 33 keys, so the flat ballot tolerance would fail an honest 14-key block and cost a paid parser call and then a dropped member; downstream normalises the vector anyway. Labelling is documented in `docs/numeric_pipeline.md` "Per-bin elicitation on enumerable grids"; this section covers only how the block is read.

`extract_pmf(text, grid: PmfGrid, parser_llm, *, prompt_notes, question_id, model_name)` runs the same four rungs as `extract_mc` and returns `ExtractionOutcome[PmfForecast]`. `PmfForecast.declared` is the platform's own PMF shape: `[below, p_0, ..., p_{N-1}, above]`, length `N + 2` for an `N`-bin grid, in grid order, as declared and BEFORE the floor blend in `numeric.pmf_cdf`; a closed bound's tail slot is 0.0. This is the vector Mantic exposes for every resolved forecast (`disagreement_forecasts.forecasts[].pmf`), so the `MEMBER_FORECAST` `raw` field and the platform's own record of the forecast read alike.

Both value-producing rungs (the block rung via `PmfStructured.bin_probs`, the LLM salvage rung via `structured_parse.BinProbability`, a `label` / `probability` pair whose list wrapper `BinProbabilityListWrapper` keeps the constrained schema from falling back to a bare list) run one conversion, `_pmf_from_pairs`, whose rules mirror the multiple-choice canonical map:

- **Every value is range-checked before folding.** `_pmf_from_pairs` refuses a non-finite or out-of-[0, 1] probability on the pair it arrived on (`block key '0' probability -1.0 outside [0, 1]`), BEFORE duplicate folds are summed, so `-1` on `"0"` and `2` on `"0.0"` cannot cancel into a clean 1.0 on one bin (the codex Wave C bug hunt's repro). The block rung's schema already enforces the range, so this bites on the LLM rung, whose `BinProbability.probability` is an unconstrained float.
- **Fold-matching on both sides.** A block key and every grid key are folded through `numeric.pmf_grid.fold_bin_label` (the option-label fold, commas dropped, anything that parses as a float re-rendered canonically), so `"7.0"`, `" 7 "` and `"55,000"` match `"7"` and `"55000"`, `" 2026-09-16 "` matches `"2026-09-16"`, and `Above_Range` matches `above_range`. The grid's keys are folded too because on a timestamp-style grid a label's own fold differs from it (`T` and `Z` lowercase). Dates fold as text: `2026-9-16` or `Sep 16` is an unknown key and falls through, exactly as an unmatched MC key does; the prompt's verbatim key list is the mitigation, and `rung=llm` on `EXTRACTION_RUNG` monitors the salvage rate.
- **Duplicate folds sum** onto one bin (the MC rule).
- **An unknown key fails the rung** (`block key 'x' matches no bin of this grid`), and **a reserved key on a closed bound fails the rung** with its own reason (`block declares 'below_range' but the question's lower bound is closed`), so a prompt regression shows up in the failure text.
- **Every grid key must be present.** A block truncated before its last bins is not caught by the repair rung's numeric-literal check when the cut lands between bins (the raw candidate then carries no incomplete literal, `json_repair` closes the braces, and the result is a valid PARTIAL declaration); the every-key rule (`block is missing bin(s) [...]; a partial declaration cannot be published`) is what makes it fall through to the LLM rung instead of publishing. A cut inside a number is refused by `_repair_infidelity_reason` as on every other block type. The same rule is what makes the salvage parser's notes (`forecaster_runners.build_pmf_parse_notes`) tell it to LEAVE OUT a key the forecaster gave no probability rather than write 0 for it: a bin the forecaster ruled out IS 0, a stated probability, but an unstated open tail is unknown, and leaving it out lets the every-key rule drop the member instead of publishing an `above_range` nobody declared. Until 2026-09-09 the notes said both "never fill it in" and "a key the forecaster gave no probability is 0", and a parser obeying the second sentence could invent exactly that tail; `tests/test_forecaster_runners.py::TestBuildPmfParseNotes` pins the wording and `tests/test_pmf_extraction.py::TestLlmRung` pins that a salvage missing the tail still fails.
- **The fidelity validator** (`_make_validate_pmf`) then requires the `N + 2` length, every entry finite in [0, 1], and the sum within the same key-scaled tolerance of 1.0 (`pmf_prob_sum_tolerance(len(grid.keys))`), on every rung: the LLM rung decodes under a schema and must emit numbers, so a salvage that sums to 0.5 is not a reading.

A `question_type: numeric` or `date` block on a per-bin ladder is refused by the `question_type` mismatch guard like every other cross-type block. Pins: `tests/test_pmf_extraction.py` (grids built directly from the frozen `PmfGrid` dataclass), `tests/test_structured_output_schema.py::TestPmfStructured`, `tests/test_structured_parse.py::TestBinProbabilityWrapper`.

## The two per-forecast markers

Every successful extraction emits one `EXTRACTION_RUNG: question=... model=... qtype=... rung=... block_present=...` INFO log line — this is the drift-signal telemetry that superseded the deleted shadow-divergence comparison (`qtype=date` since 2026-09-08 and `qtype=pmf` since 2026-09-09, both additive tokens in a `\S+` field). The line's `qtype` has always been the BLOCK type the ladder parsed, so on a per-bin date question it reads `qtype=pmf` while the `MEMBER_FORECAST` line beside it reads `qtype=date`: join the QUESTION type from the member line, never from this one. Watch `rung=llm` salvages and `block_present=false` in prod logs; those are the two symptoms that indicate a forecaster stopped emitting a well-formed block. Beside it, since 2026-09-02, one `MEMBER_FORECAST: question=... model=... role=member|stacker qtype=binary|multiple_choice|numeric|date raw=... published=...` INFO line per forecast VALUE (since 2026-09-09 a per-bin member's line also carries `elicitation=pmf`, and its `raw` is the `N + 2` declared PMF vector rather than percentile pairs; the field is ABSENT on a percentile member, and absent means percentiles, so a reader that keys on it must treat a missing field as the percentile elicitation rather than as unknown) (since 2026-09-08 a numeric or date line ends with two additive fields, `oor_low=<f> oor_high=<f>`, the built CDF's mass below and above the question's range, whose per-question twin on the published aggregate is the `NUMERIC_AGGREGATE` marker; the aggregate marker also carries the pre-floor pair `oor_low_raw=<f> oor_high_raw=<f>` and `tail_floor=<f>`, since on Mantic the published aggregate's open tails are raised to `MANTIC_OUT_OF_RANGE_TAIL_FLOOR`, see `docs/numeric_pipeline.md` "Step 11") (`metaculus_bot/member_forecast.py` `format_member_forecast_marker`; emitted by the three runners in `forecaster_runners.py` for every member, by `stacking.py` for the stacker's binary and MC output, and by `aggregation_pipeline._run_stacking_numeric` for the stacker's numeric output, since that is where its percentiles are sanitised). `raw` is the value the extraction ladder read off the rationale before any clamp, renormalise or sanitise; `published` is what the runner hands onward. Binary carries a probability each (`raw=0.005 published=0.02`); MC the option-probability vector in `question.options` order (`raw=[0.9,0.005,0.095]`), which the ladder hands back as `ExtractionOutcome[McForecast].value.declared_probs` beside the constructible list (`McForecast.option_list`; the pairing is the MC outcome's TYPE, so no consumer checks for it), because a `PredictedOptionList` is clamped on construction and the runner never holds the raw vector on the list itself (on the LLM rung's strict sub-path it is the parser's output after ft's construction clamp); numeric the declared `[percentile, value]` pairs with the percentile as the block's decimal (`raw=[[0.025,9.2],...]`, never the percent label, whose float multiply leaves `10.000000000000002` on the 0.1 anchor) and `published` the post-`sanitize_percentiles` list. Both values are whitespace-free compact JSON literals kept VERBATIM in the archive through the spec's per-spec `raw_fields` (the global `_RAW_FIELDS` is keyed by name and `THIN_PUBLISH_FLOOR` spells a float field `raw` too), so a consumer always `json.loads` them; harvested as `member_forecast`. The numeric line precedes the unit-mismatch guard on purpose: a member that guard withholds still leaves its raw declaration, which is exactly what an audit of the guard needs, and the drop is in `FORECASTER_DROPS` (restrict to members that reached the aggregate via `FORECASTERS_SURVIVED`'s `models`). The reason is the 2026-09-02 clip-threshold re-read (what a looser `BINARY_PROB_MIN` would have done): no marker carried a member's value on every question (`EXTREME_CALL` only past the band, `THIN_PUBLISH_FLOOR` only the lone-survivor case, the runner's own `Forecasted URL` line the CLAMPED value with no model name), so a raw binary probability was recoverable only from the published comment's per-rationale fenced block, which is middle-trimmed at `COMMENT_CHAR_LIMIT`, publishes a stacked question's members as sub-blocks, and carries the block only since 2026-05-19. That left 74 of 451 resolved binaries with any raw value and the 377 older ones with none anywhere; on the 179 block-era records the block-aware trim did preserve every bulleted member's block on binary, MC and discrete questions, while 9 of 50 numeric comments had lost members to the retired tier-2 block schema (`mixture_components` / `tails` blocks with no `declared_percentiles`, or blocks with trailing content that fail `json.loads`). Receipts: `scratch/residual_2026-09-01/clip_threshold/member_value_gap.py`.
## The ladder: design notes

Rationale that used to live in comments inside `metaculus_bot/value_extraction.py`. Each item names the function or constant it explains; the code carries a one-line pointer here.

**`_JSON_STRING_RE`, the string mask behind `_numeric_tokens_outside_strings`.** It reads string literals in either quote style. Raw candidates are exactly the malformed blocks the repair rung exists for, and single-quoted output is the commonest malformation, so a reader that recognised only double quotes would walk single-quoted prose as value position and read numbers out of it. The trailing `(?:"|\Z)` alternative keeps an unterminated final string, which is the truncated-payload case the whole fidelity check exists for, inside the literal rather than spilling its contents into value position.

**A schema-valid but unusable candidate is spent (`_try_candidate`).** When the strict parse succeeds and conversion or validation then fails, the function returns rather than handing the same candidate to the repairer, because `json_repair` cannot alter JSON that already parses. The live example is a numeric block carrying only `_REQUIRED_NUMERIC_PERCENTILES`, the schema's floor, instead of the full `STANDARD_PERCENTILES` set the pipeline needs. The caller falls back to the next candidate.

**Candidate selection order (`_run_ladder`, rungs 1 and 2).** The order comes from `extract_json_block_candidates`: tagged ```json fences before untagged ones, and within a tier the last block by position first, because the prompt asks for the STRUCTURED FORECAST block last. Position is the primary signal, and validity, whether strict or repaired, only breaks ties. Each candidate is offered to both deterministic mechanisms before the next one is tried (`_try_candidate`), which is what candidate-major means. Running the two mechanisms as separate passes over the whole candidate list published superseded drafts: a valid earlier draft satisfied the strict pass, so a malformed final block never reached the repairer that exists to fix exactly that, for instance a trailing comma.

**The `BLOCK_FALLBACK` line.** When the value comes from a candidate other than the position-last one, `_run_ladder` logs one `BLOCK_FALLBACK: question=... model=... qtype=... skipped=<n> rung=... reasons=...` INFO line. It is INFO rather than WARNING because the observed case is a trailing schema-example block, which is benign. Watch it alongside `EXTRACTION_RUNG`: a rising rate means the prompt's block-last contract is eroding.

**The multiple-choice LLM rung (`extract_mc`'s `_llm` closure).** The salvage rung mirrors the pre-ladder two-stage tolerant parse: strict `PredictedOptionList` first, then the loose `list[OptionProbability]` form. Both sub-paths route through `build_mc_prediction`, so parser output with case or prefix-variant option names such as "option a" is canonicalized onto the question's option set before `_validate_mc`'s exact set comparison. The strict result needs that pass as much as the loose one does, because the parser's `prompt_notes` explicitly allow case-insensitive matches and the result therefore cannot be trusted to carry canonical spellings. The block rung, by contrast, deliberately bypasses `build_mc_prediction`, because its `_normalize_name` strips a leading "Option " token and an option may literally be named "Option A"; the fold-on-both-sides rule it uses instead is documented on `mc_processing.fold_option_label`.

## Block schemas: design notes

Rationale that used to live in comments inside `metaculus_bot/structured_output_schema.py`. Each item names the function or constant it explains; the code carries a one-line pointer here.

**`_MAX_STRUCTURED_BLOCK_BYTES`.** `_decode_structured_payload` refuses a raw block over 200,000 bytes before it calls `json.loads`. A legitimate structured block is under 5 KB, so a payload that large is almost always a malformed rationale rather than a big forecast, the canonical shape being an unclosed fence that swallowed half the transcript into the block body. The cap exists so the parse is bounded in memory and time instead of trusting whatever the fence handed us, and a refusal is logged and falls through to the next rung rather than raising.

**`_readable_optional_float`, the `OverflowError` branch.** `json.loads` decodes an integer literal of any length into an arbitrary-precision Python int, and `float()` on one past roughly 308 digits raises `OverflowError`. Pydantic converts only `ValueError` and `AssertionError` into a `ValidationError`, so an uncaught `OverflowError` from inside a validator propagates out of `model_validate` and past `parse_structured_payload`, whose `except` clause catches `ValidationError` only. That is strictly worse than the strict code this lenient reader replaced, which turned the same input into a clean rejection the extraction ladder could fall through. Catching it and reading the value as absent restores that behaviour.

**`NumericOutcomeType` and `_NUMERIC_OUTCOME_TYPES`.** The discrete-versus-continuous vocabulary is declared once, as a `Literal`, and `_tolerate_unknown_outcome_type` reads its accepted set off that `Literal` with `get_args` rather than restating the two strings. A restated copy fails asymmetrically: a third outcome type added to the annotation would pass validation and then be silently nulled by the validator whose copy had not been updated. The derived set is a tuple rather than a frozenset on purpose, because membership on a tuple compares by equality, so an unhashable declaration such as a list or a dict reads as unrecognised instead of raising `TypeError` out of the validator.

**`BinaryStructured.base_rate_anchor` and `criteria_clauses`.** Retiring these two telemetry slots from the prompt on 2026-09-02 was safe because the structured block is written after the forecast is already fixed, so both slots only re-keyed prose the rationale already contained, and their only reader was a telemetry line behind a flag that every production workflow pins off. The fields remain on the model, optional and tolerant, because the published comments that carry them are strict-parsed by `performance_analysis`; the per-field counts and dates are in the `BaseRateAnchor` and `CriteriaClause` docstrings.

**`parse_structured_block`.** Selection is validity-aware rather than position-only: validating only the last block by position let a trailing schema-recap or example block shadow a valid forecast earlier in the rationale, so the parser walks `extract_json_block_candidates` best-first and keeps the first that validates for the caller's `question_type`. Among valid blocks the last by position still wins and tagged fences still outrank untagged ones. A candidate that failed but was recovered by a later valid one is not a WARNING; a single INFO records that trailing blocks were skipped, which is the signal that the prompt's block-last contract is eroding. Failure logging is gated to the last candidate the loop tries, and the common case is a rationale with exactly one candidate, where the only index is also the last one, so single-block logging is unchanged by the multi-candidate walk. Selection here is STRICT-only, so the publish path does not use it: `value_extraction._run_ladder` also repairs each candidate in place, and callers of this function read a block for telemetry or analysis, where an unrepaired None is the honest answer.

**`extract_json_block_candidates` and `extract_json_block`.** The ranking is explicitly tagged ```json fences (case-insensitive, any whitespace) first, then untagged fences whose body begins with `{`, and within each tier the LAST block by document position first, because the prompt asks for the STRUCTURED FORECAST block last, so among equally valid blocks the last one is the intended forecast. `extract_json_block` is the schema-blind first pick of that list, kept for callers that need only a block's raw text, such as peeking at a self-declared `question_type` before the schema is known.

**`parse_structured_payload` and `log_failures`.** The flag gates the WARNING lines on every failure path (size cap, decode, shape, `question_type`, validation). A caller probing several candidate blocks for the first valid one passes `log_failures=False` so a rejected-then-recovered candidate does not emit a WARNING as if extraction had failed; the telemetry-strip RECOVERY log is not gated, since it reports on a block that is returned. The flag is also handed to `model_validate` as validation context, because a lenient validator that reads an unusable declaration as absent logs from inside the model, where it cannot otherwise see it: without that, a suppressed probe still emitted an operator-facing WARNING about a block it was about to discard.

**`_tolerate_unknown_outcome_type`.** `outcome_type` gates discrete snapping, and the block value exists to save a parser-LLM call (`forecaster_runners._resolve_discrete_vote`). Under a bare `Literal` a near-miss spelling ("integer", "discrete", "count") took the PERCENTILES down with it: the numeric block has no strip-and-retry, so the whole forecast dropped to LLM salvage AND the parser call fired anyway for the type. Reading the strays as None costs exactly the one parser call the field was meant to save. The stray is logged at WARNING with its raw value, because a spelling the roster starts using is a prompt signal, but only where the caller wants failure logging: with `log_failures=False` in the validation context it drops to DEBUG, since otherwise a misspelling warned on superseded draft blocks and twice per numeric forecast on the publish path about a block that validates and publishes fine.

**`DateStructured`.** Its values go through `numeric.date_axis.parse_forecast_date` and nothing else, which is what makes the block the truncation guard for dates. The repair rung's fidelity check reads only numbers outside string literals, so a rationale cut mid-date (`"0.99": "2027-06-1`) is invisible to it: `json_repair` closes the quote and hands back an invented `"2027-06-1"`. Here that value fails to parse and the whole block fails, which sends the ladder on to the LLM rung rather than publishing a date nobody declared. Non-string values are rejected for the same reason: pydantic would otherwise read a bare `2027` as a unix timestamp in 1970. There is no `outcome_type` because integer snapping on an epoch axis is meaningless and the date runner never records a discrete vote.

**`_retry_without_binary_telemetry`.** Strip-and-retry for malformed BINARY telemetry (2026-07-08). `base_rate_anchor` and `criteria_clauses` are telemetry only, nothing reads them to clamp or mutate a forecast, yet without this a malformed payload (`criteria_clauses: null` where the prompt said to omit the key, or a reversed `{low > high}` anchor) dropped the ENTIRE block, including a perfectly good `posterior_prob`, and so silently removed the forecaster from the cross-model aggregation: a pure formatting bug in a telemetry field could shift stacker input, violating the telemetry rollout's zero-behaviour-change invariant. It is deliberately not a schema-wide before-validator, which would silently coerce bad clause probabilities and miss the reversed anchor; only the two telemetry fields are dropped, so any error in a core field still surfaces as None. Since 2026-09-02 the prompt no longer asks for either field, so on a fresh forecast this never fires; it survives for archived blocks and for a model that emits one from habit.

**`_validate_probability_dict` and `_Probability`.** The ballot (`option_probs`) and the per-bin block (`bin_probs`) share one probability-vector validator: non-empty, no blank key, every value in [0, 1] (which also refuses NaN), and a sum within the field's own tolerance of 1.0 (the flat `_MC_OPTION_PROB_SUM_TOLERANCE` for the ballot, `pmf_prob_sum_tolerance(key_count)` for the block). The label in each error is the field's name, and the ballot's four messages are pinned byte-for-byte in `tests/test_structured_output_schema.py::TestMultipleChoiceOptionProbs` because they are archive-visible failure text; before the extraction the two copies had already drifted (one carried a dead `isinstance(key, str)` check that a mode-after validator on `dict[str, float]` can never fail). The value type of both fields, and of `posterior_prob`, is `_Probability`, a float whose before-validator refuses a JSON boolean: pydantic's lax float reads `true` as 1.0 and `false` as 0.0, which would publish a bin or option the forecaster never priced as certain (the codex Wave C bug hunt's repro). Integer literals `0` and `1` still read as floats. The telemetry-only probability fields (`StatedPrior.prob`, `ScenarioBranch.prob`, `CriteriaClause.prob`, `BaseRateAnchor`) stay on plain `float` on purpose: refusing a boolean there would cost a forecast for a field nobody reads.

**`_object_without_duplicate_keys` and the `question_type` guard (`_decode_structured_payload`).** `json.loads` runs with an `object_pairs_hook` that raises on a repeated key in any object, nested ones included; the failure is logged under the existing "Malformed JSON in structured block" line with the hook's text (`duplicate key '0'`), so it needs no new marker. The default decoder keeps the last value, which would have read `{"posterior_prob": 0.2, "posterior_prob": 0.8}` as 0.8. Resolving which value the forecaster meant is the parser LLM's job, from the prose, which is why the repair rung refuses the collapsed block too (see "The ladder", rung 2). The `question_type` guard keys on `"question_type" in payload`: an absent key is filled in with the caller's type so the discriminator resolves, and any present value that is not the caller's type, `null` included, is the mismatch refusal; `payload.get` conflated the two and let `null` pass as an omission. One archive consequence: `performance_analysis.declared_value_recovery` uses `parse_structured_block` as its strict rung, so an archived comment whose block repeats a key now falls to its later rungs (the prose value lines, then a tolerant raw `json.loads` that is last-write-wins, which is what the bot itself published at the time).

## The LLM salvage rung: design notes

Rationale that used to live in comments inside `metaculus_bot/structured_parse.py`.

**`_build_constrained_llm`.** The constrained parser client's sampling arguments are deliberate rather than incidental. `temperature=None` is redundant against forecasting-tools 0.2.92, whose `GeneralLlm` constructor already defaults temperature to None; it was a hard 0 before 0.2.92, and the argument is kept explicit as a pin that holds provider-default sampling if a future version flips the default back. Reasoning models are meant to defer to provider defaults here, which is also why no `top_p` is set. `role="parser"` puts the constrained primary and the `structure_output` fallback on the same `CREDIT_ROLE_SPEND` tier, the one `PARSER_LLM` bills to, because they are one parsing job.

**`_LIST_WRAPPERS`.** `response_format` needs a single `BaseModel`, so each `list[X]` output type (`Percentile`, `IsoDatePercentile`, `OptionProbability`, `BinProbability`) is parsed through a wrapper model with one list field. One table maps the item type to the pair `(wrapper, field name)`, and `parse_structured` unwraps with `getattr(parsed, field)`. Until 2026-09-09 the wrapper choice and the unwrap were two parallel `if` chains keyed on the same four classes: adding the per-bin salvage type meant editing both, and a wrapper that landed in the first chain but not the second fell off the end of the `try` suite without returning, straight into the `structure_output` fallback, a second paid parser call on every salvage with nothing logged. `tests/test_structured_parse.py::TestListWrapperTable` pins that every entry's field is annotated `list[item type]`.

**`parse_structured`.** The primary path sends a deliberately thinner prompt than `structure_output` does: constrained decoding enforces the schema at the model, so the prompt needs only the rationale text plus any caller instructions, with no schema description or worked example to carry. The `except` around the primary path is a boundary, not a bug: constrained decoding is an optimization over the framework fallback, so any failure at all (schema validation, a refusal, truncation, a provider error) must degrade to `structure_output` rather than fail the forecast, which is why the catch-all there is intentional and carries the harness-scan exemption.

## What the ladder does NOT decide

Discrete-integer snapping is decided separately by the C3 block-read in `forecaster_runners.run_numeric_forecast` — it reads `NumericStructured.outcome_type` directly before falling back to a parser LLM call for `OutcomeTypeResult`, and the ladder does not touch that path.
