### Important (should fix)

- **[F1]** `metaculus_bot/numeric/config.py:77` Max step is not floored to 9 decimals, so a concentrated fine-grid forecast is rejected 400 and the question is forfeited (confidence: 96) — concurred: concern-2, reproduced in triage
  - Problem: `grid_step_constraints` returns `max_step = 0.2 * 200 / inbound`, matching the server's cap formula, but the server compares `np.round(np.diff(cdf), 9)` against the UNROUNDED cap. At inbound=450 (the live Preseason 2 bitcoin question, 451-point CDF) the cap is 0.08888888888888889 and `round(0.0888888888888889, 9) = 0.088888889`, which is greater. The repo's own max-step repair clips over-cap bins to exactly `max_step`, so every clipped bin lands precisely in the rejected zone. I reproduced it through the real pipeline: three normals with sd $250 on the live grid produce `CDF_MAXSTEP_CLIP` with 5 over-cap bins, and the repo's own server replica then rejects each member and the median aggregate with "step above server max 0.08888888888888889: max pmf 0.088888889 at 226". 601, 721 and 1501 points round above the cap the same way; 201 and 2001 do not, which is why this never fired on Metaculus.
  - Consequence: the POST returns 400, `publish_hardening._should_retry` deliberately does not retry a non-retryable 4xx, and the forecast plus its comment are lost after the research and three forecaster calls were already paid for. Threshold is a peak bin above 8.889%, i.e. an ensemble sd under roughly 4.5 bin widths.
  - Fix: `max_step = min(1.0, math.floor(0.2 * 200.0 / inbound * 1e9) / 1e9)`. One line, no new branch, and I verified it is a no-op on every Metaculus grid (201 to 0.2, 101 to 0.4, 13 to 1.0) while making the tight 451, 2001 and 201 cases pass for both bound polarities. Then update `test_exact_server_formulas` (it will fail at 451 otherwise) and add a concentrated fine-grid case, because every existing case uses a broad normal so the cap never binds.

- **[F2]** `scripts/reconcile_credit_spend.py:78-94` (trigger at `metaculus_bot/credit_telemetry.py:188`) The donated-key skip line breaks the settled-spend chain for interleaved Metaculus runs (confidence: 95) — concurred: grounding, reproduced in triage
  - Problem: the new donated-key skip logs `CREDIT_BALANCE: key=donated phase=start skipped (donated routing disabled)`, which parses into an archive record with `phase` set and `usage: null` (I confirmed the parse). Mantic run logs land in the same telemetry archive as Metaculus runs. `_paired_snapshots` pairs any run with both phases regardless of whether a balance was read, and `reconcile` computes settled spend as `next_start_usage - this_start_usage`, bailing to None when the successor's usage is None.
  - Consequence: every Metaculus run whose chronological successor is a Mantic run loses its settled donated-key spend, plus a spurious all-None row appears. I reproduced it: inserting a usage-less Mantic run between two tournament runs turns the predecessor's settled spend from 3.0 into None. With the Mantic crons at :17/:47 against the tournament's :03/:23/:43 and the cup's :13/:33/:53, that is roughly a third of donated-key runs, and this is the tool that watches the Metaculus-donated credit budget.
  - Fix: in `_paired_snapshots`, skip usage-less START records only (`if phase == "start" and record.get("usage") is None: continue`), because only the start usage feeds the settlement chain. Verified by simulation: settled reads 3.0 / 2.0 / None with the patch versus None / spurious-row / 2.0 / None today. The reviewer's original variant (requiring usage on both phases) mis-attributes on the archive's existing null-END row, so use the narrow form.

- **[F3]** `metaculus_bot/numeric/validation.py:169-173` (reached via `metaculus_bot/mantic.py:114`) The discrete rewrite silently discards `zero_point`, so a log-scaled fine-grid question would publish a wrong distribution (confidence: 85) — concurred: codex-bugs. Pre-existing branch, newly reachable.
  - Problem: rewriting Mantic's `quantitative` type to `discrete` routes every fine-grid question into the discrete numeric path. `check_discrete_question_properties` treats any question whose `cdf_size != 201` as discrete and forces `zero_point = None`; `build_cdf_value_grid` then builds a LINEAR value axis instead of the geometric one the platform declares. The submitted CDF is a list of probabilities the server maps positionally onto ITS bin edges, so on a `[1, 1e6]` zero_point question at 451 points the published median reads 1.18 instead of the declared 1000, with no error and no marker. Metaculus never hit this because its log-scaled questions always carry `inbound_outcome_count=200` (so `cdf_size == 201` and the branch is skipped) while its discrete questions are small integer grids with a null zero_point. Mantic is where the two combine.
  - Reachability: latent, not observed. All four Preseason 2 questions and every zero_point question in 283 archived Metaculus records carry `inbound_outcome_count=200`. What this diff adds is the Mantic mode and first-class fine-grid support that make the combination possible, and the loss is total when it fires.
  - Fix: delete the `if is_discrete and zero_point is not None:` arm outright, leaving the genuine singularity guard (which the deleted arm currently short-circuits for discrete questions), and change `pipeline.py:154` from `np.linspace(...)` to `build_cdf_value_grid(lower, upper, zero_point, target_cdf_size)` so `declared_percentiles` sits on the axis `get_cdf()` reports. No coarseness threshold: the branch's 2025 rationale was the assumption that discrete questions are never log-scaled, not a numerical requirement. The verifier ran the deletion: 8,204 passed with only the one behaviour pin failing.
