##### forecasting-tools 0.2.92 already models date questions as "numeric questions whose x-axis 
forecasting-tools 0.2.92 already models date questions as "numeric questions whose x-axis is epoch seconds": DateQuestion carries datetime bounds, NumericDistribution.from_question converts them with .timestamp() and sets is_date=True, the CDF is evaluated on a uniformly spaced grid of cdf_size points, and DateReport inherits NumericReport.publish_report_to_metaculus verbatim, posting the same positional continuous_cdf list of floats. The Metaculus backend (which Mantic forked) validates a date submission with the identical type-agnostic continuous_validation, so on the publish side there is nothing date-specific to build. The work is entirely upstream of that: the repo's numeric pipeline is typed on NumericQuestion and reads question.upper_bound/lower_bound as floats, and a DateQuestion carries datetimes there, so the first thing that touches it (Pydantic construction of NumericDistribution, or the `timedelta > 100` comparison in calculate_bounds_buffer) raises. I found 11 distinct places in the repo where a DateQuestion breaks or is silently mis-handled, four of them hard raises on the MEDIAN path that every prod question takes.
-- FACTS --
FRAMEWORK / DATA TYPES: DateQuestion (.venv/lib/python3.12/site-packages/forecasting_tools/data_models/questions.py:473-527) subclasses MetaculusQuestion + BoundedQuestionMixin with `upper_bound: datetime`, `lower_bound: datetime`, `open_upper_bound: bool`, `open_lower_bound: bool`, `zero_point: float | None = None`, `cdf_size: int = 201`. Unlike NumericQuestion it has NO nominal_upper_bound / nominal_lower_bound fields and no previous_forecasts field, and it does NOT override give_question_details_as_markdown.
FRAMEWORK / BOUNDS PARSING: DateQuestion.from_metaculus_api_json (questions.py:500-524) calls the shared BoundedQuestionMixin._get_bounds_from_api_json, which float-casts `api_json["question"]["scaling"]["range_max"]` / `range_min` (questions.py:426-433), then runs each through MetaculusQuestion._parse_api_date (questions.py:212-221), whose float/int branch is `return pendulum.from_timestamp(date_value)`. So a date question's bounds arrive on the wire as EPOCH SECONDS and the framework converts them to tz-aware UTC datetimes. MetaculusQuestion has an `add_timezone_to_dates` model_validator (questions.py:124-126) so the bounds are always tz-aware.
FRAMEWORK / CDF SIZE: DateQuestion reads cdf_size through the shared BoundedQuestionMixin._get_cdf_size_from_json (questions.py:444-453): `outcome_count = api_json["question"]["scaling"]["inbound_outcome_count"]`, None -> 200, then `cdf_size = outcome_count + 1`; a missing key logs a warning and returns 201. Identical to numeric.
FRAMEWORK / PERCENTILE TYPES (question 1): `Percentile.value` is typed `float` (numeric_report.py:46-52). There is a separate `DatePercentile` model with `value: datetime` (numeric_report.py:66-81), but it exists ONLY as the structure_output parser target inside the template bots; no NumericDistribution or DateReport field ever holds one. A DateReport's `prediction.declared_percentiles` and `prediction.get_cdf()` are lists of ordinary float-valued Percentiles whose values are EPOCH SECONDS, and the published cdf is a positionally-keyed list of plain floats.
FRAMEWORK / DATE->FLOAT SEAM: NumericDistribution.from_question (numeric_report.py:255-297) is the single conversion point: `is_date = isinstance(question, DateQuestion)`; if is_date it sets `upper_bound_float = question.upper_bound.timestamp()` and `lower_bound_float = question.lower_bound.timestamp()`, else uses the raw floats, and forwards `is_date=is_date`. `is_date: bool = False` is a real NumericDistribution field (numeric_report.py:99) whose only consumer is the readable-prediction formatter.
FRAMEWORK / UNIFORM SPACING (question 2, answer: YES): NumericDistribution.get_cdf (numeric_report.py:334-390) computes `cdf_eval_locations = [i / (cdf_size - 1) for i in range(cdf_size)]` and maps each to a value with _cdf_location_to_nominal_location (numeric_report.py:604-617), which is `scaled_location = range_min + (range_max - range_min) * cdf_location` when zero_point is None. Verified empirically: a 2026-01-01 -> 2030-01-01 DateQuestion with cdf_size=201 produced 201 points whose consecutive value diffs were the single constant 631152.0 seconds = (1893456000 - 1767225600)/200, with x[0] = 2026-01-01T00:00:00Z and x[-1] = 2030-01-01T00:00:00Z.
FRAMEWORK / ZERO_POINT ON DATES (question 3, answer: YES structurally): DateQuestion has a real `zero_point: float | None` field, _get_bounds_from_api_json reads scaling.zero_point for it, from_question forwards it, and both _nominal_location_to_cdf_location (numeric_report.py:472-500) and _cdf_location_to_nominal_location (numeric_report.py:604-617) apply the deriv_ratio geometric transform whenever zero_point is not None, with no is_date special-casing. The server matches: utils/the_math/formulas.py unscaled_location_to_scaled_location (github.com/Metaculus/metaculus main, lines 77-103) branches only on BINARY / MULTIPLE_CHOICE then applies the geometric formula for every continuous type; QUESTION_CONTINUOUS_TYPES (questions/models.py:486-490) is [NUMERIC, DATE, DISCRETE]; and QuestionWriteSerializer.validate (questions/serializers/common.py:216-231) imposes no date-specific zero_point restriction. So a log-scaled date question is representable end to end, though it would mean a geometric axis over epoch-seconds-since-1970 and is almost certainly never authored.
FRAMEWORK / STANDARDIZATION: NumericDistribution._standardize_cdf (numeric_report.py:528-602) is entirely date-agnostic; it operates on probability heights only (rescale to bounds, a 0.988/0.989/0.99 mixture with a `0.01 * location` uniform component, then a bisection search for the PMF max-step cap). NumericDefaults.get_max_pmf_value scales the 0.2 cap by DEFAULT_INBOUND_OUTCOME_COUNT / inbound_outcome_count (numeric_report.py:31-43).
FRAMEWORK / READABLE OUTPUT: NumericReport.make_readable_prediction (numeric_report.py:664-680) is the ONLY is_date consumer: when `prediction.is_date` it renders `datetime.fromtimestamp(percentile.value, tz=timezone.utc).strftime("%Y-%m-%d %H:%M:%S UTC")`, otherwise `round(value, 6)`. Verified: a date distribution built via from_question printed "- 10.00% chance of value below 2027-01-01 00:00:00 UTC".
FRAMEWORK / PUBLISH: DateReport (numeric_report.py:722-724) is `class DateReport(NumericReport)` with only two field overrides (`question: DateQuestion`, `prediction: NumericDistribution`). Verified at runtime that `'publish_report_to_metaculus' in DateReport.__dict__` is False and `DateReport.publish_report_to_metaculus is NumericReport.publish_report_to_metaculus` is True. That inherited method (numeric_report.py:682-719) extracts `cdf_probabilities = [p.percentile for p in prediction.get_cdf()]` and calls post_numeric_question_prediction, which POSTs `{"continuous_cdf": cdf_values}` after asserting 0<=x<=1 and monotonicity (helpers/metaculus_client.py:267-283). The value axis is never transmitted.
FRAMEWORK / REPORT MAPPING: DataOrganizer.__TYPE_MAPPING maps DateQuestion -> DateReport with test_post_id 4110 (data_organizer.py:62-71). get_report_type_for_question_type is what ForecastBot._run_individual_question uses to build the report (forecast_bot.py:375-377 and 406-412) and what _create_comment uses for make_readable_prediction (forecast_bot.py:594, 621, 653). DateQuestion is in the `QuestionTypes` union (data_organizer.py:43-48) and DateReport in `ReportTypes` (data_organizer.py:50-52).
FRAMEWORK / DISPATCH ORDER: ForecastBot._make_prediction (forecast_bot.py:497-518) tests Binary, MultipleChoice, NumericQuestion, ConditionalQuestion, then DateQuestion. The order is safe because DateQuestion does NOT subclass NumericQuestion (DiscreteQuestion does, questions.py:635, which is why discrete falls into the numeric branch). The base `_run_forecast_on_date` (forecast_bot.py:531-535) is a non-abstract method that raises NotImplementedError, annotated `-> ReasonedPrediction[NumericDistribution]`.
FRAMEWORK / OFFICIAL DATE PROMPT (question 4): template_bot_2026_summer._run_forecast_on_date (forecast_bots/official_bots/template_bot_2026_summer.py:416-471) asks for SIX percentiles (10/20/40/60/80/90) as literal dates, with the rules "The dates must be written in the format of YYYY-MM-DD. If hours matter, please append the date with the hour in UTC and military time: YYYY-MM-DDTHH:MM:SSZ. No other formatting is allowed." and "Always start with a lower date chronologically and then increase from there." Bound messages come from _create_upper_and_lower_bound_messages (same file, 513-537), whose DateQuestion branch uses `question.upper_bound.date().isoformat()` and an EMPTY unit_of_measure. The identical implementation exists at template_bot_2026_spring.py:419-474 and template_bot_2025_fall.py:544-599; research_only_bot_2025_fall.py:177 and uniform_probability_bot.py:93 also implement it (the latter builds a uniform distribution from lower_bound.timestamp() + fraction * range).
FRAMEWORK / OFFICIAL DATE PARSING (question 4): _date_prompt_to_forecast (template_bot_2026_summer.py:474-509) does NOT use PredictionExtractor. It calls `structure_output(reasoning, list[DatePercentile], ...)` with the instruction "The output is given as dates/times please format it into a valid datetime parsable string. Assume midnight UTC if no hour is given", then converts with `Percentile(percentile=p.percentile, value=p.value.timestamp())` and hands the list to NumericDistribution.from_question. LIVE TRAP: DatePercentile is not run through add_timezone_to_dates_in_base_model (that validator lives only on MetaculusQuestion, questions.py:124-126, and MetaculusClient, helpers/metaculus_client.py:101), so a naive datetime parsed from "2030-03-01" gets `.timestamp()` in the HOST's local timezone. Verified locally: datetime(2030,3,1).timestamp() = 1898582400.0 versus the UTC-aware 1898553600.0, an 8-hour (28,800 s) offset on this Pacific-time laptop. Harmless on a UTC GitHub runner, wrong anywhere else.
FRAMEWORK / EXTRACTOR CANNOT PARSE DATES: PredictionExtractor.extract_numeric_distribution_from_list_of_percentile_number_and_probability is annotated `question: NumericQuestion | DateQuestion` (helpers/prediction_extractor.py:229-251) but its line parser is a pure number regex (_parse_numbers_from_line, prediction_extractor.py:274-296) with no date handling, so the union in that signature is misleading.
SERVER SIDE: the Metaculus backend's ForecastWriteSerializer.continuous_validation (questions/serializers/common.py:514-582, fetched from raw.githubusercontent.com/Metaculus/metaculus/main) is completely type-agnostic: length must equal inbound_outcome_count + 1, per-bin pmf in [round(0.01/inbound, 9), 0.2 * 200 / inbound], cdf[0] >= 0.001 or == 0.0 by open/closed lower bound, cdf[-1] <= 0.999 or == 1.0 by upper bound. Date questions are in QUESTION_CONTINUOUS_TYPES so they take exactly this path. In the read serializer (common.py:88-118) scaling.range_min / range_max stay RAW epoch floats for date questions and nominal_min / nominal_max equal them: the datetime formatting via `format_value` is applied ONLY to `continuous_range`, and nominal_min/max are overridden only for DISCRETE. DEFAULT_INBOUND_OUTCOME_COUNT = 200 (questions/models.py:21).

-- RECOMMENDATIONS --
Model the date question as "a NumericQuestion-shaped view whose axis is epoch seconds" ONCE, at the edge, instead of threading DateQuestion through 40+ NumericQuestion-typed signatures. Build an adapter that takes a DateQuestion and satisfies the numeric contract (float lower_bound/upper_bound from .timestamp(), open bounds, zero_point, cdf_size, id_of_question, page_url, unit_of_measure), run the existing numeric pipeline against it, and convert back only where a human or the API sees values. This is exactly what forecasting-tools itself does at numeric_report.py:255-297, so it is consistent with Mantic's and Metaculus's own implementation rather than a hack, and it makes the PCHIP builder, grid_step_constraints, safe_cdf_bounds, aggregate_numeric and the publish path all work unmodified.
Whichever adapter shape you choose, make `is_date=True` reach the final NumericDistribution. That is a one-argument change in create_pchip_numeric_distribution (metaculus_bot/numeric/pchip_processing.py:262-275) plus the same in create_fallback_numeric_distribution, and it is the difference between a published comment reading "50.00% chance of value below 2027-07-01 00:00:00 UTC" and one reading "1815091200.0". The framework already does the formatting (numeric_report.py:664-680); nothing else in the comment path needs to change.
Fix the four hard raises first, because they sit on the MEDIAN path every prod question takes: aggregation_pipeline.py:533 (_combine_by_type gate), aggregation_pipeline.py:92 (get_threshold_for_question), spread_metrics.py:232 (compute_spread) and aggregation_pipeline.py:172 (run_stacking). If the adapter is a genuine NumericQuestion instance all four resolve for free, which is a strong argument for making it a real NumericQuestion rather than a duck-typed shim.
Do NOT leave _type_gate_enabled (stacking_route.py:82-90) fail-open for dates. Its `return True` default makes a date question stacking-eligible, contradicting the prod-wide stacking-off posture. Either add a DATE_STACKING_ENABLED_ENV entry to _STACKING_ENV_BY_QUESTION_TYPE, or (if the adapter makes date questions read as numeric) confirm they pick up the numeric gate. Pin it with a test asserting a date question skips stacking under the default env.
Re-derive the bounds buffer for a wide axis instead of accepting the flat 1.0 at bounds_clamping.py:19. On an epoch-second axis a one-second clamp tolerance turns "model named a date one day outside a closed bound" into a dropped forecaster. The existing relative branch (range_size * BOUNDARY_SAFETY_MARGIN, i.e. 1%) is the right shape for a date question; whatever you pick, make the threshold explicit and constant-backed in numeric/config.py rather than inheriting the `> 100` heuristic by accident.
Write the date prompt to ask for the SAME 13 STANDARD_PERCENTILES the numeric prompt uses, not the framework's six, and require strict ISO-8601 UTC ('YYYY-MM-DD' or 'YYYY-MM-DDTHH:MM:SSZ'). Then parse to tz-AWARE UTC datetimes explicitly before calling .timestamp(): the framework's own converter (template_bot_2026_summer.py:504-509) has a live local-timezone bug because it calls .timestamp() on a possibly-naive datetime, an 8-hour error on a Pacific-time machine. Add a test that a naive ISO date parses to the UTC epoch rather than the local one.
Add a DateStructured block (question_type: Literal["date"], declared_percentiles as percentile -> ISO-8601 string) rather than reusing NumericStructured, which is extra="forbid" with a closed question_type literal (structured_output_schema.py:293-302). Register it in the value_extraction ladder so the EXTRACTION_RUNG telemetry and the fenced-block convention hold for dates as they do for numerics.
Widen metaculus_bot/question_types.py's QuestionType literal to include "date" and have question_type_of return it. This is purely additive for the marker contract (scripts/telemetry/markers.py parses qtype as \\S+ at lines 320, 655 and 1116) and it fixes the TOOLS_USED marker lying on date questions via the None-qtype path in tool_runner._feature_enabled (tool_runner.py:127-130).
Suppress the half-step nominal-bound derivation for date questions (numeric/utils.py:233-250). The backend derives nominal min/max only for DISCRETE (serializers/common.py:104-106), so for a date question nominal == range, and any Mantic date question with a non-200 inbound_outcome_count would otherwise get prompt bounds shifted inward by half a bin. Also consider renaming the _build_discrete_distribution log line (numeric/pipeline.py:156-160), which will report "Discrete build" for every non-201-grid date question.
Do NOT add DateReport to publish_hardening._PATCHED_REPORT_TYPES. DateReport inherits the already-patched NumericReport.publish_report_to_metaculus, so the thread offload and the close-time gate already cover it; adding it would raise the AttributeError at publish_hardening.py:441-446 because DateReport.__dict__ has no publish method. If you want a regression pin, extend the coverage assertion at tests/test_publish_hardening_concurrency.py:172-176 to check that DataOrganizer's DateReport resolves to an already-wrapped inherited method.
Decide date-question backtesting scope explicitly. Enabling it means touching backtest/question_prep.py:450 (allowed_types), :290-303 (_group_by_question_type), :505-545 (_extract_ground_truth, including the `assert not isinstance(typed_res, datetime)` at :538) and the CRPS/log-score helpers in backtest/scoring.py, plus the parallel gates across ablation/. For q651 that means calendar day D = 2026-09-08 + k days occupies bucket k+1 = cdf[k+1] - cdf[k], so a forecaster certain of 2026-09-16 (k=8) should put its mass in cdf[9]-cdf[8], i.e. cdf[0..8] near 0 and cdf[9..12] near 1. There is one real off-by-one hazard I could not close from public data: no day-granularity date question has resolved yet, and all 88 in-range legacy resolutions landed strictly inside a bin, so the on-edge behaviour is unexercised. If Mantic writes the resolution string as the answer date's own UTC midnight rather than any later instant, the right-closed rule pulls it into the PREVIOUS bin — but that reading is provably broken as a design (2026-09-08 and 2026-09-09 would collide in bucket 1 and bucket 12 would be unreachable), so next-midnight or any mid-day instant is almost certainly what Mantic does.

AUTHORITATIVE RESOLUTION-TO-BIN MAPPING, FROM THE METACULUS BACKEND. https://raw.githubusercontent.com/Metaculus/metaculus/main/utils/the_math/formulas.py, unscaled_location_to_bucket_index (lines 130-148): u < 0 returns 0; u > 1 returns N+1; u == 1 returns N; otherwise max(int(u*N + 1 - 1e-10), 1). The module's own header comment (lines 25-33) states it explicitly: 'a scaled_location equal to range_min maps to bucket_index 1, not 0. Bucket 1 is a closed-on-both-sides interval [range_min, range_min + step]. Bucket 0 is reserved for outcomes strictly below range_min. This mirrors the CDF convention where cdf[0] is P(x < range_min) and cdf[1] is P(x <= range_min + step).' So inbound bucket b covers (continuous_range[b-1], continuous_range[b]] — RIGHT-closed, left-open — except bucket 1, which also includes the left edge.
WHAT A SUBMITTED CDF VALUE AT INDEX i MEANS. cdf[0] = P(outcome strictly < range_min). cdf[i] = P(outcome <= continuous_range[i]) for i >= 1. cdf[N] = P(outcome <= range_max) = 1 - (mass above the upper bound). The mass that scores bin b is cdf[b] - cdf[b-1]. The Mantic guide states the same asymmetry in prose ('the first value of the CDF array we are going to build will be the probability that the temperature is less than (not equal to) -40. The last value will represent the probability that the temperature is less than or equal to 110', mantic_openapi.yml:64-68) and spells out the closed-lower-bound consequence: 'if you believe there is a 70% chance the outcome is exactly the lower bound, set cdf[1] = 0.7 (and cdf[0] = 0.0)' (mantic_openapi.yml:70-76, repeated at 145-150).
I CONFIRMED THE WHOLE INDEXING CHAIN AGAINST MANTIC'S OWN REPORTED SCORES. For each resolved date question I computed the bucket index with the backend formula, built pmf = [cdf[0]] + [cdf[i]-cdf[i-1] for i in 1..N] + [1-cdf[N]] from aggregations.recency_weighted.latest.forecast_values, and applied the baseline formula from https://raw.githubusercontent.com/Metaculus/metaculus/main/scoring/score_math.py:99-103 (baseline = 0.05 if the bucket is 0 or N+1, else (1 - 0.05*open_bounds_count)/N; score = 100*ln(pmf[bucket]/baseline)/2). This reproduced the API's reported spot_baseline_score within 0.5 points on 192 of 192 scoreable questions, with ZERO mismatches (17 skipped: 8 annulled, 8 unresolved practice, 1 open). Script: /tmp/mantic_probe/verify_score.py. This validates the PMF layout, the N+2 slot count, the bucket formula and the out-of-bounds handling simultaneously.

THE ON-EDGE OFF-BY-ONE HAZARD IS REAL BUT THE BROKEN READING IS SELF-REFUTING. If Mantic writes the resolution string as the answer date's OWN UTC midnight (e.g. exactly '2026-09-16T00:00:00+00:00'), the right-closed rule puts it in bucket 8 = cdf[8]-cdf[7], one bin early. I enumerated that hypothesis across all 12 dates on the real grid: 2026-09-08 (u=0.0, clamped to bucket 1) and 2026-09-09 (u=1/12, bucket 1) COLLIDE, every later date is shifted one bucket early, and bucket 12 becomes unreachable, so 12 possible answers would map onto only 11 scoring slots. Under the alternative (resolution written at the next midnight, or at any instant strictly inside the answer day) the mapping is a clean bijection: date 2026-09-08+k to bucket k+1 for all k = 0..11. SERIES 2 RULES DOC, SECTION 5 (PRECISION OF RESOLUTION). /tmp/mantic_probe/ref/doc_1-L5Ap8BoA46kvi4gbDSUTDJPovpuu5daBJgnFqlCHgg.txt lines 81-132. Question writers pick the expected resolution precision; total bins must not exceed 2,000; date questions have a MINIMUM bin width of 1 day. MONTHS ARE IN THE DESIGN DOC BUT NOT IN THE API. MONTH GRANULARITY WOULD REQUIRE A BACKEND CHANGE, SO NON-UNIFORM DATE EDGES CANNOT HAPPEN TODAY. day (86,400 s) and week (604,800 s) are both constant, so both produce uniform epoch grids. Calendar months are 28-31 days and cannot. The shared scaling math supports only two shapes — linear and logarithmic (formulas.py:77-128) — and the bucket lookup runs through scaled_location_to_unscaled_location, which applies whichever of those two formulas the question declares. A non-uniform calendar-month grid would be neither, so its bucket indices would come out wrong. Empirically the only existing non-uniform continuous_range values in the whole Mantic corpus are the 14 log-scaled numeric questions (zero_point = 0.0), and the log formula reproduces their edges to 2e-15. Conclusion: if and when months ship, they will need either a third scaling mode or (far more likely, per section 5) 1-day forecast bins aggregated up at scoring time.

-- RECOMMENDATIONS --
Treat scaling.continuous_range as the ONLY source of truth for the bin grid on every Mantic continuous question, and never re-derive edges from nominal_min/nominal_max/precision/date_granularity. Three independent reasons: the date convention is left-aligned (range_max = nominal_max + one bin) while the discrete convention is center-aligned (range_max = nominal_max + half a bin); the live Preseason 2 discrete question 650 violates the documented discrete convention outright, with range_max = nominal_max - precision/2 and nominal_max not representable; and continuous_range is the field whose length the API validator ties the CDF length to. Read the grid, assert len(continuous_range) == inbound_outcome_count + 1, and build the CDF at those exact points.
Fix the CDF length to inbound_outcome_count + 1, not 201, everywhere in the publish path. Question 651 needs 13 values and question 650 needs 451. Scale the two validity thresholds with N too: minimum CDF step is 0.01/N (0.000833 for a 12-bin question, sixteen times the familiar 0.00005) and the standardizer's step cap is 0.2*(200/N). Any hardcoded 201, 0.00005 or 0.2 in the numeric pipeline is a latent Series 2 rejection.
Encode the bin-mass convention once, in one named helper, with the right-closed semantics spelled out: the mass for the outcome in bin k (0-based over continuous_range) is cdf[k+1] - cdf[k], the interval is (continuous_range[k], continuous_range[k+1]] with the left edge belonging to bin 0 only, cdf[0] is the strictly-below-lower-bound mass, and 1 - cdf[N] is the above-upper-bound mass. Port the exact backend expression max(int(u*N + 1 - 1e-10), 1) rather than reimplementing rounding, including the u == 1 special case that maps range_max into bin N-1 rather than out of bounds. I reproduced 192 of 192 real Mantic baseline scores with this, so it can be pinned by a regression test against archived score_data instead of trusted on reading.
For a day-granularity date question, map a target calendar date D to k = (D - date(nominal_min)).days and put its mass in cdf[k+1] - cdf[k], then ASSERT that continuous_range[k] equals midnight of D. That assertion is the whole safety story: it fails loudly if Mantic ever changes the alignment, and it is cheap. Do not compute k from a float epoch ratio, because k is exactly the case where u lands on a bin edge and the 1e-10 fudge decides the answer.
Build a real DateQuestion path rather than mapping dates onto the existing numeric percentile machinery unchanged. The forecaster prompt should ask for a probability per calendar day (or per named bin edge) on a day-granularity question, because with 12 bins the platform's own scoring is a discrete PMF over 12 named dates and asking for 13 continuous percentiles then PCHIP-interpolating throws away the one thing the new format exists to capture. Keep the percentile path for the 200-bin legacy shape, which is genuinely continuous. Branch on question.date_granularity, and raise on any value outside {'', 'day', 'week'} so a future 'month' cannot be silently mishandled.
Make the above-upper-bound mass a first-class output on date questions, not a residual of the tail-widening code. Half of all resolved Mantic date questions (101 of 200) resolved above_upper_bound, so 1 - cdf[N] is more often the scoring slot than any inbound bin. On an open-upper-bound date question the prompt should elicit P(the event does not happen inside the window) directly, and the publish path should place that number in 1 - cdf[N] rather than letting it fall out of an interpolation.
Change the question-discovery query to stop filtering on forecast_type, or add 'quantitative' to it. forecast_type=discrete and forecast_type=numeric each return zero Preseason 2 posts, and forecast_type=quantitative returns exactly one platform-wide, so any enumeration built on the old two values will silently skip every Series 2 quantitative question. An unfiltered tournaments=<slug> query returned all four Preseason 2 posts, which is the simpler and more future-proof shape. Verify this against whatever the mantic-client agent built.
Handle the four non-timestamp resolution sentinels ('above_upper_bound', 'below_lower_bound', 'annulled', 'ambiguous') and the two-case anomaly where an out-of-range timestamp is stored verbatim instead of a sentinel (posts 627 and 576, both open-lower-bound). Any backtest or scoring code that assumes a resolved date question yields a parseable in-range timestamp will crash on 109 of 200 real questions and silently mis-score 2 more. Parse timestamps with datetime.fromisoformat, which handles Mantic's space-separated 'YYYY-MM-DD HH:MM:SS+00:00' form; do not assume a 'T' separator or an epoch number.
Add an integration fixture built from the real question 651 payload (already saved at /tmp/mantic_probe/dates/date_posts.json and /tmp/mantic_probe/d651.json) and assert end to end that a forecaster certain of 2026-09-16 produces a 13-value CDF whose bin-8 mass is the maximum and which passes cdf[0] == 0.0, cdf[12] == 1.0 and min-step 0.000833. That single test pins bin alignment, CDF length, threshold scaling and closed-bound handling at once. Add a second fixture from question 650 for the 451-point log-free discrete case.
When question 651 resolves on 2026-09-20T12:00Z, pull its resolution string and its own reported baseline score and check them against both off-by-one hypotheses. That is a free, unauthenticated GET and it is the only way to close the on-edge question definitively. Do not build for date_granularity = 'month' or for non-uniform date bins now. Months appear in the Series 2 rules doc but not in the API enum, and calendar-month edges are expressible under neither of the two scaling modes the shared backend math supports, so shipping them would require a platform change that would be visible in the spec first.
